# 首屏加载优化方案（四个方向，可单选也可组合）

> 约束前提：**功能、交互逻辑、UI 设计全部保持不变**。下面四个方案都只改「内容什么时候到、以什么顺序到、要下载多少代码」，不改最终的视觉结果和操作方式。
> 唯一需要你点头的差异点，会在每个方案里单独标出来。

---

## 一、先看实测现状（本次对生产构建 `pnpm build` 的统计）

| 项目 | 实测值 |
| --- | --- |
| 首页首屏 JS | 17 个文件，**902 KB（未压缩）/ 294 KB（gzip）** |
| 首屏 CSS | 85 KB（未压缩） |
| 预渲染 HTML | 13 KB，**里面没有任何卡片文案**（"留言墙""最新文章""身份认证"都搜不到） |
| React + Next 运行时 | 210 KB raw / 67 KB gzip |
| motion（动效库）核心 | 129 KB raw / **43 KB gzip** |
| 农历库 + motion 辅助 | 59 KB raw / 22 KB gzip |
| 首页卡片数 | 10 张，`order` 最大 8 |

### 慢在哪：三段叠加，不是单一原因

1. **HTML 是空的。** 首页所有卡片都依赖客户端算坐标（`use-center` 初始 x=0、y=0），而 `Card` 组件在 `x===0 && y===0` 时**直接 return null**。所以用户拿到的 HTML 只有一层背景，必须等 294 KB gzip 的 JS 下载、解析、执行完，才出现第一张卡。
2. **出现之后还要排队。** `Card` 用 `order * ANIMATION_DELAY(0.1s)` 逐张挂载，order 8 的那张要等 **0.8 秒**；导航卡自己还有一层 `useEffect → setShow` 门控；社交图标是一串 `setTimeout` 逐个冒出。所以"页面能用"的时间 = JS 到达时间 + 0.3~0.9 秒。
3. **首帧还有额外开销。** `neuro-noise` 的 WebGL 全屏着色器在 mount 时同步编译并立刻绘制，10 张卡又都带 `backdrop-blur-xl`，叠在持续 30fps 重绘的画布上；另外 `favicon.png` 有 222 KB，每次进站都要拉。

> 补充：如果你说的"首次加载慢"是本地 `pnpm dev` 第一次打开（3~10 秒白屏），那是 Turbopack 编译时间，与本方案不是同一件事，末尾单列了一段对策。

## 二、四个方案对比

| | 方案 A 时序收敛 | 方案 B 服务端直出 | 方案 C 首屏拆包 | 方案 D 渲染开销 |
| --- | --- | --- | --- | --- |
| 解决什么 | 出现后还要等 0.3~0.9s | HTML 里什么都没有 | 294 KB JS 要下载解析 | 首帧 shader 编译 + 合成开销 |
| 改动文件 | 5 个组件 | 5~6 个文件 + 布局常量 | 6~8 个文件，换 1 个依赖用法 | 1~2 个文件 |
| 首屏 JS 变化 | 不变 | 不变 | **−60~70 KB gzip（约 −22%）** | 不变 |
| 体感收益 | 大（最直接） | 最大（根治） | 中（弱网/旧机收益放大） | 中（低端设备明显） |
| 视觉差异 | 入场节奏变快 | 无 | 无（缓动曲线需对齐） | 背景动效晚 0.2s 启动 |
| 风险 | 极低 | 中低 | 中 | 中 |
| 工期 | 0.5 小时 | 1~1.5 天 | 1~2 天 | 0.5~1 天 |

## 三、方案 A｜时序收敛（最小改动，先把体感救回来）

**思路**：不动代码结构，只把"明明已经准备好了，却还故意等一会儿"的地方去掉。

1. `src/components/card.tsx` —— 去掉 `show` 门控（现在要等 `x/y` 非 0 且等定时器才挂载）。改为拿到坐标立刻渲染，入场动画（0.6→1 缩放 + 淡入）原样保留。
2. 错峰延迟收敛：`order` 0~8 现在等于 0~0.8 秒。改成 `Math.min(order, 3) * 0.1s`，最多 0.3 秒，仍是"一张接一张"，只是不再拖到快 1 秒。
3. `src/components/nav-card.tsx` —— 删掉 `const [show, setShow]` 和那个 `useEffect(() => setShow(true))`，首帧直接渲染。
4. `src/app/(home)/social-buttons.tsx` —— 把 `setTimeout` 链换成 CSS `animation-delay`（上限 120ms），容器不再门控。
5. `src/app/(home)/write-buttons.tsx` —— 同样删掉 `show` 门控。
6. 顺手：`Head` 里加 `<link rel="preload" as="fetch" href="/blogs/index.json" crossorigin>`，并把 `use-blog-index` 的 `cache: 'no-store'` 改成默认缓存（数据更新最多晚一次刷新生效，换来省掉一次冷连接和"加载中…"占位）。

**预期**：所有卡片可见时间整体前移 0.3~0.7 秒，首屏从"一张张冒出来"变成"一下就齐了"。
**会变的**：入场错峰节奏（这是唯一影响"观感"的地方，形状、时长、缓动都不变）。若你想保留原来的慢节奏，A2 版本只做第 1、3、4、5 项，不动 delay。

## 四、方案 B｜服务端直出（首帧就有内容，根治"白屏等 JS"）

**思路**：卡片的位置本来就是一串常量算出来的，完全可以用 CSS 表达式在服务端算好，让 HTML 一到达就是完整页面。

1. 默认坐标改成 CSS `calc`：把 `center.x + offset` 换算成 `left: calc(50% + Npx)`、`top: calc(50% - 24px + Npx)`（N 由 `card-styles.json` 里的 width/height/`CARD_SPACING` 推出来，都是常数）。
2. `Card` 不再 `return null`，服务端直接输出最终位置的卡片；入场动画保留（scale + fade，delay ≤ 0.2s），因为动画起点和终点现在都在正确坐标上，不会出现"从左上角飞过来"的跳变。
3. `useCenterStore` 只服务于拖拽/编辑态，等用户按下鼠标再算 px，首屏不再依赖它。
4. `NavCard` 默认位置同样走 calc（首页锚在留言墙左侧）；小屏沿用现有 `max-sm` flex 布局。
5. 文章卡三选一（按你要的"功能不变"程度排序）：
   - 最稳：只加 `preload` + HTTP 缓存，SWR 保留；
   - 更好：`page.tsx` 外层套一个 server 组件，请求时读 `public/blogs/index.json`，作为 props 传给文章卡，**彻底去掉"加载中…"占位**。代价是 `/` 从静态预渲染变成可按 ISR 刷新的路由（`revalidate = 300`），内容更新延迟最多 5 分钟（与现在打开页面才更新的体验接近）。

**预期**：首次可见内容从"JS 执行完"提前到"HTML 到达"，中端手机约省 300~600ms；文章卡不再有占位闪烁。
**风险**：10 张卡 × 桌面/平板/手机三档坐标要逐一对齐（可能差 1~2px）；拖拽、缩放手柄、编辑态保存要回归一遍。
**注意**：这一步做完，A 里的第 1、3 项会被覆盖，两个方案不要重复做。

## 五、方案 C｜首屏拆包（少下载、少解析）

**思路**：首屏只留"立刻要用的代码"，动效库和农历库都不该在这 294 KB 里。

1. **motion 退出首屏（−43 KB gzip）**：首屏只用到三种效果——卡片 `scale 0.6→1` 入场、hover `scale 1.05`、导航那个 `layoutId='nav-hover'` 滑块。前两个改成 CSS `@keyframes` 与 `:hover/:active`；滑块改成一个绝对定位 div 的 `left/top/width/height` CSS `transition`，缓动用 `cubic-bezier(.22,1,.36,1)` 近似原 spring。其余页面（/blog、/pictures、/write）继续用 motion，只是不再进首屏链路。
2. **农历库换内置表（−8~12 KB gzip）**：`lunar-typescript` 体积远大于它承担的功能（现在只用来显示"十月初七"和每一天的农历日）。换 1900–2100 的压缩数据表 + 60 行换算，`getLunarDate` 返回结构不变，显示完全一致。需要核对闰月与月首边界。
3. `sonner` 的 `Toaster` 改成首次 toast 时才动态挂载（layout 里不再静态引）。
4. 资源瘦身：`favicon.png` 222 KB → 48×48 PNG（约 3 KB）；`avatar.png` 93 KB → webp ≤30 KB（`priority` 保留）。

**预期**：首屏 294 → **约 230 KB gzip**，主线程解析与执行省 80~150ms（中端机；弱网下按比例放大）。
**风险**：motion → CSS 的缓动手感需要肉眼对齐，尤其导航滑块；农历边界要抽样对比。建议先只做 1 + 4，验证后再做 2、3。

## 六、方案 D｜渲染开销（针对"打开瞬间卡住/掉帧"）

**思路**：网络不再是瓶颈之后，首帧的 GPU/主线程开销就成了体感的一部分。

1. `src/layout/backgrounds/neuro-noise.tsx` —— 着色器启动挪到首帧之后：保留现有的静态渐变兜底，`requestIdleCallback`（2s 超时）里再创建 WebGL 上下文、编译 shader，画布淡入 200ms。最终画面完全一样，只是动效晚 0.2 秒出现。
2. 背景画布提成独立合成层（`transform: translateZ(0)`），避免 10 张卡片的 `backdrop-blur` 与动画画布同层反复重绘。
3. 自适应降档：`hardwareConcurrency <= 4` 或 `deviceMemory <= 4` 时背景降到 15fps（运动更缓，视觉差别很小）。
4. 可选（**会改视觉，默认不做**）：卡片 blur 从 `xl(24px)` 降到 `lg(16px)`，毛玻璃通透度会略有变化，需要你确认。

**预期**：首帧不再等 shader 编译；核显笔记本和安卓中低端机掉帧明显减少。Lighthouse 的网络指标不变。
**风险**：需要真机对比，模拟器看不出来。

## 七、我的建议顺序

- **想今天就看到效果**：方案 A（0.5 小时），改完立刻是"一下就齐了"。
- **想彻底解决"白屏等 JS"**：A 之后接方案 B（1 天），这一步才是根因。
- **C 独立排期**：它改善的是所有页面和弱网用户，但风险与核对成本最高，建议单独一个分支做，用 before/after 打包体积对比验收。
- **D 看真机表现**：如果你在旧笔记本/手机上确实感到"打开后卡一两秒"，优先做 D 的 1、2 两项（半天）。

## 八、验收方式（四个方案通用）

1. `pnpm build` 后记录首屏 JS 总量（脚本读 `server/app/index.html` 里的 script 列表求和），对比 gzip 体积。
2. DevTools Performance：4× CPU 节流 + Fast 4G，记录 `FCP`、`LCP`、`TBT`，以及在卡片容器上加的自定义 `performance.mark('all-cards-visible')`。
3. 视觉回归：桌面 1920/1440、平板 1024、手机 390 三档截图对比（位置、尺寸、圆角、毛玻璃、入场终态）。
4. 交互回归：拖拽/缩放手柄、导航 hover 滑块、社交图标下拉二维码、音乐卡播放、留言墙跳转。

---

## 附：如果"慢"指的是本地 `pnpm dev` 首次打开

那是 Turbopack 冷编译（首次 3~10 秒），与上面四个方案无关。对策：
- 保持 dev server 常驻，不要每次关掉重开；
- 首屏链路上的 `lunar-typescript`、`motion` 同样拖慢编译，方案 C 做完后 dev 首次打开也会快一截；
- 开发时先访问 `/about` 这类轻页面预热编译，再回首页。
